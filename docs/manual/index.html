CHAPTER 01

ツール概要・動作環境

Docker Builder Toolは、モジュールを選び、入力した設定からdocker-compose.ymlと、必要なサービスのDockerfile等を生成するデスクトップツールです。コンテナの起動や、アプリのソースコードを自動作成するものではありません。

目的必要なもの
ソースからアプリを起動するWindowsの作業フォルダに現行ソース、Node.js 22.12以上とnpm。既存の依存設定はElectron 45.0.0です。
構成ファイルを生成・保存するDocker環境は不要です。ファイルは利用者が指定した場所へ保存します。
生成構成を実際に動かす別途、Docker EngineとDocker Composeを使える環境、および必要なアプリコード・依存ファイルが必要です。
このHTMLを読む画像・CSS・JavaScriptを含むフォルダ一式と、ローカルHTMLを表示できるブラウザ。外部CDNは使用しません。

Windows配布版と同梱マニュアル

  1. インストールしたDocker Builder Toolを起動します。
  2. 「ヘルプ」→「ユーザーマニュアル」を選ぶと、既定のWebブラウザでこのマニュアルを開きます。
  3. HTML・画像・レシピは同梱されているため、閲覧にインターネット接続は不要です。外部の実行結果リンクを開く場合のみ接続が必要です。

ソースからアプリを起動する

  1. 現行ソースを展開したアプリのフォルダでターミナルを開きます。
  2. 初回、または依存関係を入れ直す際は npm ci を実行します。
  3. npm start を実行してアプリを起動します。
  4. 「ヘルプ」→「バージョン情報」で 0.3.0 Release 1 を確認します。
公開済みの配布版との違い

既存のv0.2.2の実行ファイルには、v0.3.0 Release 1のUIは含まれません。本マニュアルの対象はv0.3.0 Release 1です。

レシピの使い方

必要な追加ファイルと設定を確認し、利用する環境で起動・接続を確認してください。

CHAPTER 04

構成入力・設定確認

入力 → 確認 → チェック

  1. 「構成入力」タブを開き、「共通設定 / 構成実行」の「プロジェクト名」を入力します。サービス名等の接頭辞になります。
  2. 初期表示では先頭のモジュールだけ展開されています。各ヘッダーのモジュール名または矢印を押して開閉します。複数を同時に開けます。
  3. バージョン系列、イメージ形式 / 完全タグ、公開ポート、DB設定、データ保存方式などを確認します。
  4. 確認したモジュールの右上にある「設定確認」に手動でチェックを入れます。チェックだけではパネルは閉じません。
  5. 全件確認済みになったら「構成を実行」へ進みます。0件選択時や未確認がある間は生成できません。
チェックが外れるとき

ポート、DB名、パスワード、保存方式、イメージなど、生成に関わる設定値を変更すると、そのモジュールだけ未確認に戻ります。プロジェクト名の変更は全モジュールに影響します。開閉・同じ値の再選択・詳細情報の開閉・パスワード表示切替・コピーでは解除されません。

パスワードは表示と実データを分けて扱います

  • 初期表示はマスクです。「パスワードを表示」で表示のみを切り替えます。パネルを閉じると再びマスクされます。
  • 「コピー」はマスク中でも実際の値をコピーします。空欄では使えず、成功通知にパスワード自体は表示されません。
  • クリップボード履歴や他のアプリに読まれる可能性があります。必要なときだけコピーしてください。自動消去はしません。
  • 対象はMySQL・MariaDB・PostgreSQLのパスワード、LaravelのDBパスワード、phpMyAdminのDBパスワードです。WordPress・Redmineは選択したDBの設定を利用し、専用の秘密値入力欄はありません。
  • 画面上のマスクは暗号化ではありません。生成したComposeには必要なパスワードが平文で含まれるため、共有・公開前に内容を確認してください。

永続化とイメージ情報

独立した「永続化」タブはありません。各モジュール内の「データ保存方式」を使います。名前付きボリュームとバインドマウントでは表示項目が切り替わります。「参照」はバインド先の既存フォルダを選ぶ際に利用します。

「Dockerイメージのバージョン情報」の「オンライン更新」は、Docker Hubのメタデータを取得して選択候補を更新します。イメージやモデル自体のダウンロード・起動ではありません。取得に失敗した場合も既存キャッシュを維持します。

サポート中と安全性は別です

ランタイムのサポート状態と、CVE等の脆弱性検査結果は別の情報です。「脆弱性未検査」を安全確認済みと扱わないでください。本稿の構成例は同梱カタログを使用し、オンライン更新は押していません。

CHAPTER 05

構成を生成する

全件確認後に構成を実行

確認済み件数が全件になり、ボタンが「構成を実行」になってから押します。赤い「構成を確認」は未確認がある状態で、クリックできません。

  1. 全モジュールの「設定確認」にチェックがあることを確認します。
  2. 「構成を実行」を押します。「ファイル」→「生成開始」でも同じ確認条件が適用されます。
  3. エラーが表示された場合は、対象の入力欄へ戻って修正し、再確認します。ポート範囲・重複・DB依存・イメージの検証はチェック後も実行されます。
  4. 生成後、「生成結果」タブを開きます。
自動起動はしません

この操作は構成ファイルの生成です。Dockerコンテナを起動したり、GitHubへ自動送信・認証・Actions起動を行ったりしません。

Node.jsは利用者のアプリとpackage.json・整合するlockfileが必要です。Flaskは利用者のPythonコードと依存定義、Laravelはソース・Composer依存・APP_KEY等が必要です。アプリがこれらを完成した本番アプリとして生成することはありません。

CHAPTER 06

生成結果とファイル保存

左右で保存するファイルが異なります

  1. 左側の「生成された docker-compose.yml」でサービス名・ポート・volumes・buildを確認します。
  2. 左の「ダウンロード」を押し、OSの保存ダイアログで docker-compose.yml として保存します。
  3. 右側の「表示・保存するファイル」で、サービス別のDockerfile等を選択します。
  4. 右の内容を確認し、右の「ダウンロード」で表示中の1ファイルだけを保存します。複数ある場合は選択を切り替えて繰り返します。
  5. 「構成ファイルの配置・起動ガイド」を開き、Composeから参照できる相対配置になっていることを確認します。

ファイル名と配置も構成の一部

フォルダ設定や個別保存だけでは、複数ファイルの配置整合性は保証されません。ZIP出力・一括フォルダ保存はありません。

Windowsの保存例は %USERPROFILE%\Documents\DockerProjects\nodejs-basic\ です。「ドキュメント」がOneDrive等へ移動されている場合は実際の場所を確認してください。任意の保存先も利用できます。

DockerProjects/
└── nodejs-basic/
    ├── docker-compose.yml                    ← アプリ生成
    └── nodejs/
        ├── Dockerfile.nodejs                  ← アプリ生成
        ├── Dockerfile.nodejs.dockerignore     ← アプリ生成
        ├── package.json                      ← 利用者が準備
        ├── package-lock.json                 ← 利用者が準備
        └── server.cjs                        ← 利用者が準備

この例ではComposeの build.context: ./nodejs と build.dockerfile: Dockerfile.nodejs に合わせます。ignoreファイルも同じビルドコンテキストに、生成された名前のまま置きます。

保存先とファイル名を確認してください

OSの保存ダイアログでフォルダとファイル名を確認して保存します。複数のDockerfileがある場合も、選択を切り替えて個別に保存してください。

生成結果は編集できますが、編集後は配置ガイドとの不一致に注意してください。「クリア」や「新規構成」の前に必要な内容を保存します。

CHAPTER 07

設定・テーマ・About

「設定」→「設定...」を開く

左メニューの「フォルダ設定」と「外観」は別の確定操作を持っています。

操作確定する内容画面を閉じるか
外観の「適用」選んだテーマを即時反映・永続保存。パス入力の検証とは独立。閉じません
下部の「保存」フォルダ設定だけを検証して保存。テーマには関与しません。成功通知後も閉じません
「初期化」アプリルート以下に既定フォルダを作り、入力欄へ設定。永続保存は別途「保存」。閉じません
「閉じる」／Esc未保存フォルダ・未適用テーマの入力だけを破棄。確定済み設定は維持。閉じます

フォルダ設定

プロジェクトフォルダ、docker-compose.yml 保存場所、Dockerfile 保存場所、ログ保存場所を指定します。現行仕様では空欄を許容します。「保存」を押すと、空欄ではないパスが存在するフォルダかを検証します。

アプリのルート/
├── Project/
│   ├── docker-compose/
│   └── Dockerfiles/
└── logs/

「初期化」が作る既定の名前は上記です。既存ファイルやリンクとの衝突・書き込み権限で作成に失敗した場合は、説明を確認してください。既存ファイルを削除・上書きする操作ではありません。

保存時に不正なパスがあれば「フォルダ設定」に自動で切り替わり、問題の欄が強調され、最初の欄へフォーカスします。存在するフォルダを選ぶか、任意項目を空欄にして再保存してください。保存失敗時も入力内容は保持されます。

なお、現在の実装ではアプリ自身の docker-builder.log はこのログ保存場所に切り替わらず、開発時はアプリルート、配布版は実行ファイルと同じフォルダにあります。Aboutに表示される実際のパスを確認してください。

テーマを適用する

  1. 左メニュー「外観」を開き、9種類のテーマカードから選択します。この段階では外観は変わりません。
  2. 「適用」を押すとアプリ全体へ即時反映され、その場で永続保存されます。下部の「保存」は不要です。
  3. 「閉じる」やEscで閉じても、適用済みテーマは維持されます。適用せずに閉じた選択は破棄されます。
  4. 次回起動時も適用済みテーマが復元されます。「自動」はOSのライト／ダークに追従します。

メイン画面右上のテーマ切替ボタンも利用できます。フォルダ設定にエラーがあってもテーマの適用は独立して行えます。プレビュー機能とキャンセルボタンはありません。

Aboutとログ

「ヘルプ」→「バージョン情報」でアプリ名、現在のバージョン、開発者、ライセンス宣言、ログの実際の保存先を確認できます。バージョンはアプリ情報から自動取得されます。ISCはpackage.jsonの宣言で、独立したLICENSEファイルは現時点でありません。

GitHubリンクは固定された公開プロジェクトページを外部ブラウザで開きます。GitHub認証・トークン入力・構成ファイル送信の機能ではありません。「閉じる」またはEscで戻ります。

CHAPTER 09

エラーと対処

困ったとき原因と対応
「構成を確認」で押せない未確認が残っています。各モジュールの入力を見直し「設定確認」をチェックします。選択0件も生成不可です。
確認済みだったのにチェックが外れた実際の設定値やプロジェクト名が変更されています。変更箇所を確認して再チェックします。
ポートの重複・範囲エラー各ホスト公開ポートを1〜65535の異なる値にします。本稿のレシピは原則TCPです。TCP/UDP切替UIはありません。
DBが必要というエラーWordPress、Laravel、Redmineなどに必要な対応DBを選択し、サービス名・DB名・ユーザー・パスワードを揃えます。
Dockerfileやpackage-lock.jsonが見つからないCompose基準の相対パスと実際の配置を確認します。Node.jsのpackage.jsonとlockは利用者が整合したものを用意します。
フォルダ設定を保存できない問題の欄と下部の説明を確認し、存在するフォルダまたは空欄に修正します。設定ファイルへの書き込み権限も確認します。
画面が表示されてもDB連携できないDBの準備完了を待ち、接続先はコンテナ内のlocalhostではなくComposeのDBサービス名にします。HTTP成功だけでSQL成功とは扱いません。
バインドマウントしたらファイルが消えたように見えるホストのマウントがイメージ内ファイルを隠している可能性があります。データ削除と決めつけず、ホスト側の内容・権限・配置を確認します。
イメージ更新が失敗する／古い・未検査表示通信・配布元の制限、カタログ状態を確認します。未検査は安全確認済みではありません。サポート切れは避け、例外を安易に使わないでください。

生成後にDocker環境で確認する手順

docker compose config -q
docker compose up -d --build
docker compose ps
docker compose logs --tail=100
docker compose down

構成フォルダで実行します。追加の compose.manual.yml があるレシピでは、全コマンドで -f docker-compose.yml -f compose.manual.yml を併用します。レシピごとのURLやSQL確認も実施してください。

データを残す停止を基本に

上記のdownには -v を付けていません。-v は名前付きボリュームのデータも削除するため、利用者の環境で不用意に実行しないでください。公開ポートやダミーパスワードは、本番利用前にアクセス制限・秘密値管理を含めて見直してください。

応用と補足資料

レシピの実動作検証結果

検証結果：OK 35／FAIL 0。検証環境：GitHub Actions / Ubuntu Docker（2026年10月28日確認）。生成した構成の起動・応答・必要なサービス連携と後片付けを確認しました。Dockerfileがある20件はビルド成功、既成イメージのみの15件はビルド対象外です。

Jenkins Pipeline実行、Ollamaのモデル推論、PortainerのDocker管理接続は今回の検証対象外です。利用者が追加するアプリや設定を含む所定の条件での結果であり、本番環境での動作を保証するものではありません。

Redmine（プロジェクト管理）課題管理アプリ
WordPress（CMS）Apache内蔵CMS
Jenkins（CI サーバ）ジョブ実行・開発検証
Ollama（ローカル LLM）ローカルモデルAPI
SteamCMD（ゲームサーバ用）ゲーム資材の取得ツール
Let's Encrypt（Certbot）証明書取得用ワンショット処理
  • LaravelはPHP公式CLI＋開発サーバーのHTTP 8000が基本です。PHP-FPMをHTTPポートとして公開する方式ではありません。本番用構成ではありません。
  • Certbotの証明書発行、Nginx/Apache側のHTTPS連携は公開ドメイン・DNS・到達性・設定が必要で、このマニュアルの実動作検証範囲に含みません。
  • Portainerは初期UIまでの例で、生成ComposeはDockerソケットを自動マウントしません。そのままでDocker管理が完成するとは扱いません。
  • OllamaはAPI構成が対象です。モデル取得・GPU・推論の動作は別途準備と確認が必要です。
