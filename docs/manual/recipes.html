難易度は、何を自分で扱うかで決めます

級は学習順序の目安です。コンテナの数や性能の順位ではなく、この説明を再現するために必要な知識・追加設定・切り分けの複雑さで判断します。複数の条件に当てはまる場合は、より難しい側に合わせます。

級必要な知識・作業選ぶ目安
初級設定値の入力、ファイル配置、単体または独立したサービスの基本応答。提供サンプルをそのまま使い、独自の連携コードは追加しません。Docker構成の生成・保存から学びたい方。
中級DB／キャッシュ接続、環境変数、依存パッケージ、1段のプロキシ、管理UIの初期化。サービス名やログから接続先を切り分けます。単体サービスを扱えて、サービス間の連携へ進みたい方。
上級3層以上の通信、DBとキャッシュの整合、既存フレームワークの依存・初期化、複数のデータ領域のバックアップと復旧。設定・コードを横断して調べます。複数サービスの起動後の問題や、データの扱いまで学びたい方。

たとえばNginx＋Node.jsの独立HTTPは初級ですが、Nginx→Node.js→MySQLと通信をつなぐ構成は上級です。Laravelのようにソース・依存・初期化が必要な例も上級としています。各レシピの「難易度の理由」を確認してください。

      動作の確かめ方と切り分け

      1. PowerShellで Invoke-RestMethod http://localhost:18180/health を実行し、okがtrueになるまでログを見ながら待ちます。起動直後だけの503を恒常エラーと判断しないでください。
      2. Invoke-RestMethod http://localhost:18180/value を繰り返します。初回はvalueが42、sourceがdatabaseとなり、キャッシュ有効中はsourceがcacheになります。
      3. Invoke-RestMethod -Method Post -Uri http://localhost:18180/value -ContentType 'application/json' -Body '{"value":43}' を実行します。DB更新後、cacheがinvalidatedになることを確認します。
      4. 再びGETし、valueが43になることを確認します。DBへの書き込みとキャッシュの失効を別々に追ってください。
      5. 任意の障害学習として docker compose -f docker-compose.yml -f compose.manual.yml stop nginx-nodejs-postgresql-redis-redis を行い、GETがDBへフォールバックし、/healthが503になることを確認します。その後 docker compose -f docker-compose.yml -f compose.manual.yml start nginx-nodejs-postgresql-redis-redis で戻します。利用中の他環境では行わないでください。

      この設計で理解すること

      Redisは正本ではなくキャッシュです。更新とキャッシュ削除の間の競合、削除失敗ではTTLの10秒程度、古い値が返ることがあります。厳密な整合性や耐障害性を保証する設計ではありません。DB障害でもキャッシュが残っていればGETが値を返す場合があるため、/healthと合わせて判断します。FlaskとNode.jsのHTTPサーバーは学習用途で、本番向けサーバー構成ではありません。

      停止時はデータを残すdownを使い、値が残ることも確認してください。共通のエラー対処は操作ガイドを参照できます。

      動作の確かめ方と切り分け

      1. PowerShellで Invoke-RestMethod http://localhost:18280/health を実行し、okがtrueになるまでログを見ながら待ちます。起動直後だけの503を恒常エラーと判断しないでください。
      2. Invoke-RestMethod http://localhost:18280/value を繰り返します。初回はvalueが42、sourceがdatabaseとなり、キャッシュ有効中はsourceがcacheになります。
      3. Invoke-RestMethod -Method Post -Uri http://localhost:18280/value -ContentType 'application/json' -Body '{"value":43}' を実行します。DB更新後、cacheがinvalidatedになることを確認します。
      4. 再びGETし、valueが43になることを確認します。DBへの書き込みとキャッシュの失効を別々に追ってください。
      5. 任意の障害学習として docker compose -f docker-compose.yml -f compose.manual.yml stop nginx-flask-postgresql-redis-redis を行い、GETがDBへフォールバックし、/healthが503になることを確認します。その後 docker compose -f docker-compose.yml -f compose.manual.yml start nginx-flask-postgresql-redis-redis で戻します。利用中の他環境では行わないでください。

      この設計で理解すること

      Redisは正本ではなくキャッシュです。更新とキャッシュ削除の間の競合、削除失敗ではTTLの10秒程度、古い値が返ることがあります。厳密な整合性や耐障害性を保証する設計ではありません。DB障害でもキャッシュが残っていればGETが値を返す場合があるため、/healthと合わせて判断します。FlaskとNode.jsのHTTPサーバーは学習用途で、本番向けサーバー構成ではありません。

      停止時はデータを残すdownを使い、値が残ることも確認してください。共通のエラー対処は操作ガイドを参照できます。

      動作の確かめ方と切り分け

      1. http://localhost:18380/ を開いてWordPressの初期設定を行い、投稿と画像アップロードを1件ずつ作成します。http://localhost:18083/ は別ポートのphpMyAdminで、Nginx配下へ自動統合する構成ではありません。
      2. phpMyAdminで対象DBとWordPressのテーブルを確認します。管理画面の公開範囲と権限を見直してください。
      3. 投稿・アップロード等の操作と外部からのアクセスを止め、PowerShellで ./backup.ps1 を実行します。backup/database.sql と backup/wordpress-files.tar.gz の両方を保存します。SQLだけでは画像ファイルを復元できません。
      4. 復旧の練習は元の環境を down で停止し、-p manual-recovery などの別Composeプロジェクト名で新しいボリュームを作って行います。元のボリュームを消す down -v は使いません。同じポートを使うため元の環境とは同時起動しません。
      5. 新しいプロジェクトでMariaDBを起動し、SQLをコンテナへコピーしてインポートします。次にWordPressを起動してファイルを戻し、Nginxを起動します。以下の具体例を参照し、失敗時は後続へ進まないでください。
      6. 復旧後、同じ投稿と画像が開けること、管理者でログインできることを確認します。ファイルが存在するだけで復旧成功とは判断しません。
      別プロジェクトへの復旧コマンド例（PowerShell）
      $restoreArgs = @('-p','manual-recovery','-f','docker-compose.yml','-f','compose.manual.yml')
# 元のプロジェクトをdownで停止した後、新しいDBを起動する。
docker compose @restoreArgs up -d nginx-wordpress-mariadb-admin-mariadb
# DBの準備完了をlogsで確認してからインポートする。
docker compose @restoreArgs logs --tail=100 nginx-wordpress-mariadb-admin-mariadb
docker compose @restoreArgs cp ./backup/database.sql nginx-wordpress-mariadb-admin-mariadb:/tmp/restore.sql
docker compose @restoreArgs exec -T nginx-wordpress-mariadb-admin-mariadb sh -c 'mariadb --user="$MYSQL_USER" --password="$MYSQL_PASSWORD" "$MYSQL_DATABASE" < /tmp/restore.sql'
docker compose @restoreArgs up -d nginx-wordpress-mariadb-admin-wordpress
docker compose @restoreArgs cp ./backup/wordpress-files.tar.gz nginx-wordpress-mariadb-admin-wordpress:/tmp/restore-files.tar.gz
# Nginxをまだ起動せず、WordPressへアクセスしない状態で展開する。
docker compose @restoreArgs exec -T nginx-wordpress-mariadb-admin-wordpress tar -C /var/www/html -xzf /tmp/restore-files.tar.gz
docker compose @restoreArgs up -d nginx-wordpress-mariadb-admin-nginx nginx-wordpress-mariadb-admin-phpmyadmin
