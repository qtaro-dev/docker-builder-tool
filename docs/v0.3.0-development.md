### オンライン方式の採用理由と信頼境界

Phase 1では管理された署名付きカタログ配信を比較・推奨したが、今回の実装では**公式配布レジストリへの直接取得**を採用した。配信サーバーや署名鍵・公開ワークフローを新設せず、出所の固定されたタグ情報だけを更新できるため。任意JSON配信サイトを信用する実装にはしていない。

通信先は固定した`https://hub.docker.com/v2/namespaces/<許可namespace>/repositories/<許可repository>/tags`と、その完全タグの詳細APIのみ。Docker Official Imagesはlibrary、各製品の配布は固定namespaceを使用する。SteamCMDは既存コミュニティ配布者であり、Valve公式と表示しない。[Docker公式API仕様](https://docs.docker.com/reference/api/hub/latest/operations/ListRepositoryTags/)

TLS証明書検証を明示的に有効にし、redirectは拒否する。15秒の各要求期限、2MiBの応答上限、Content-Type/Encoding、最大100タグ、許可タグ規則、要求タグと詳細応答の一致、sha256形式、Linux amd64とplatform digestを検証する。候補タグはAPIが実際に返した名前のみを採用し、系列とvariantの文字列から合成しない。応答に含まれる任意URL・コード・サポート状態・脆弱性判定は取り込まない。

最終カタログもschemaVersion、許可キー/slot、重複、文字数・件数、日時、scan/digest整合性を検証。検索は各ポリシーの先頭100件に限定し、候補が見つからない場合は既存の完全タグを直接確認する。検索範囲外の新規系列は自動追加しない。途中失敗は全体の更新失敗として扱い、既存候補を保持する。

キャッシュは`app.getPath('userData')/image-catalog-v1.json`。一時ファイルからrenameが成功してからメモリ状態も更新する。未来日時・時刻の巻戻り・不正なデータを拒否し、起動時にキャッシュが壊れていれば同梱データへ戻る。SHA-256チェックサムはローカル破損検出用であり、配信者の電子署名ではない。配信元の真正性はHTTPSのサーバー認証と固定namespace、取得した内容の同一性はdigestに依存する。公式アカウント侵害への独立した署名検証は実装していない。

オンライン更新するのは**許可した系列/variant内の完全タグ・digest・タグ確認日時**。サポート方針・EOL日付は公式資料で確認した同梱ポリシー（2026-10-26）を使用し、更新しても保守確認日を新しく偽装しない。新しい系列・保守方針への対応はアプリのポリシー更新が必要。保守情報/タグ情報が30日超なら古い旨を表示する。

## セキュリティ表示・制限

- ランタイム系列のサポート状態とコンテナCVE検査状態を分けて表示する。ベースOS・ユーザーが追加する依存の保守を保証しない。
- EOLまたは既知High/Criticalを持つレコードは通常生成を止め、詳細を表示する。検証目的の例外確認は生成ごとに行い、永続的な全件解除はしない。不存在/未登録/不正タグは例外でも拒否する。
- 未確認・未検査・古い情報は日時と文字で表示する。脆弱性ゼロとは表示しない。
- **現在の37候補はすべて未検査**。Trivy実行・CVEデータ更新・スキャン結果の配信は未実装。High/Critical制限はスキーマと判定のテスト用データで確認しており、実イメージのCVE判定を実施したという意味ではない。更新でdigestが変わればscanは未検査に戻す。同一digestなら以前の検査結果を保持し、タグ更新だけで既知CVEを消さない。
- オフラインでは保存済みの存在確認情報を使うため、レジストリでその後削除されたタグをリアルタイムには検知できない。digestを固定しており内容の取り違えは防ぐが、実際のpullが失敗する場合がある。

## 保存手順とDockerfileの整合性

1. `docker-compose.yml`を任意のプロジェクト用フォルダへ保存する。
2. buildがある各サービスのIDと同名のサブフォルダを作成する。
3. 結果の選択欄でDockerfileと専用dockerignoreを切り替え、それぞれ下記位置へ保存する。
4. 同じサブフォルダへ、そのアプリのソース/lock/依存ファイルを準備する。
5. 実行環境で配置・依存・資格情報を確認後に`docker compose config -q`、build、起動を行う。この開発環境でDocker実動作は確認していない。

```text
project/
  docker-compose.yml
  nodejs/
    Dockerfile.nodejs
    Dockerfile.nodejs.dockerignore
    package.json
    package-lock.json
    ...アプリソース
  python-web/
    Dockerfile.python-web
    Dockerfile.python-web.dockerignore
    requirements.txt
    ...DjangoまたはFlaskソース
  laravel/
    Dockerfile.laravel
    Dockerfile.laravel.dockerignore
    composer.json
    composer.lock
    artisan
    .env
    public/、app/等
```

例：Node.jsのComposeは`build.context: ./nodejs`、`build.dockerfile: Dockerfile.nodejs`。後者はcontext基準。ビルドサービスには公式image名を併記せず、公式イメージのpullが自作ビルドを置き換えることを避ける。[Docker公式build仕様](https://docs.docker.com/reference/compose-file/build/)

専用ignoreファイルはDockerfileと同じ場所の`<Dockerfile名>.dockerignore`。`.git`、`.env`、秘密鍵、node_modules、vendor、ログ等をCOPYから除外する。アプリ固有の秘密情報は利用者が除外対象へ追加する必要があり、あらゆる秘密ファイル名を検出する機能ではない。[Docker公式context/ignore仕様](https://docs.docker.com/build/building/context/#dockerignore-files)

Composeを保存した後はDockerfileの保存ダイアログで対応するサブフォルダを候補にするが、フォルダや全ファイルの配置を自動作成・保証はしない。別の場所/名前に保存すると、想定場所と修正手順を画面に表示する。Dockerfileを先に保存した場合や、後からComposeを移動した場合も、画面の相対配置手順を必ず確認する。既存の個別保存・コピー・編集を維持する。

名前付き/appボリュームは既存コードを保持する場合があり、再ビルドだけでは更新されない。バインドマウントを使う場合は入力したマウント元にも同じソースが必要。既存ボリュームの削除やソースのコピーは自動実行しない。

**ZIP出力・フォルダ一括保存は未追加**。将来実装する場合は、上書き確認・部分失敗・リンク/パストラバーサル拒否・既存設定との整合性を別途設計する。

### Laravelの準備

PHP公式**CLI**イメージで`php artisan serve --host=0.0.0.0 --port=8000`を実行し、ホスト側ポートだけ既存入力値を使う。PHP-FPMや9000番をHTTP公開しない。PHP8.4既定、8.3/8.2も選択可。Laravel13の最低PHP8.3など、実際のcomposer.json/lockと選択PHPの互換性が必要。[Laravel公式要件](https://laravel.com/framework/docs/13.x/deployment)

Composer2は別途確認した完全タグとdigestでCOPYし、`composer install`はlockを使用する。pdo_mysql、pdo_pgsql、intl、mbstring、zip、bcmath、opcacheを追加する。アプリ固有の追加拡張やネイティブ依存は利用者の要件に合わせる必要がある。Composerやソース内スクリプトもDockerビルド環境で実行されるため、信頼するソースを用意する。

`.env`はイメージから除外し、Composeの`env_file: ./laravel/.env`から実行時に渡す。既存アプリに適したAPP_KEYを設定し、無断で鍵を生成/上書きしない。storage/bootstrap/cacheの書込み権限、セッション/cache接続先、migration、必要なフロントエンドビルドを確認する。開発用サーバーを本番へ公開しない。

MySQL/MariaDB/PostgreSQLに応じてドライバー・内部ポート・接続先を生成する。DBを複数選んだ場合はDBホストを明示する。DB側の名称/資格情報を接続設定に使用し、アプリ側へ独自入力した値が異なる場合は黙って上書きせず生成を止める。DB初期化/既存データ移行はしない。

Nginx/Apacheのリバースプロキシ設定・PHP統合は自動追加していない。CLIサーバーへ連携するならサービス名:8000のHTTP upstream設定が別途必要で、選択だけでは連携しない旨を画面にも表示する。Certbotとのchallenge/証明書共有、renew/reloadも別途設定が必要。

### Node.jsの標準と互換性

| 配置方式 | 生成するマウント | 扱い |
| --- | --- | --- |
| `image`（新しい既定） | `/app`のマウントなし | ソースと依存はイメージ内。ビルド内容を隠さず、再ビルドでコードを更新する。実行時に書くファイルの永続化は別設計 |
| `bind`（開発用） | 指定ソースを`/app`、匿名ボリュームを`/app/node_modules` | ホスト側の依存でLinux向け依存を隠さない。ソース/lockはcontextとマウント元で一致させる。依存を変更した際は再ビルドと依存用匿名ボリュームの更新が必要 |
| `named`（旧構成との互換） | 既存の名前付きボリュームを`/app` | 名前・値を保持する。古いソース/依存を保持する可能性を警告し、自動削除・移行はしない |

新規/未指定の起動コマンドは`npm run dev`。Dockerfileだけで`npm ci`を実行し、起動時の依存インストールを除いた。DockerfileのCMDとComposeのcommandは同じ共通関数を使用し、ComposeではcommandがCMDを上書きするので両方を連続実行する構成ではない。

`npm install && npm run dev`など、明示的な旧値・カスタムコマンドはそのまま保持する。旧値と利用者の意図を文字列だけで区別して変換しない。インストールを含む場合は二重実行の注意を表示する。配置方式の既存識別子`named`/`bind`、ボリューム名・ホストパスの入力欄を維持し、新規の既定値だけを変更した。設定ファイル形式の変更や、既存のローカル`settings.json`への書込みは行っていない。

ソースは利用者が準備する。package.jsonと対応するpackage-lock.json、標準設定で`npm ci`が成功すること、scripts.devまたはカスタム起動先、`0.0.0.0:3000`での待受が必要。公開ポートは入力値:3000。起動スクリプト内のポートまではアプリが書換えない。本番用のビルドや起動方式・権限設計は自動生成していない。
